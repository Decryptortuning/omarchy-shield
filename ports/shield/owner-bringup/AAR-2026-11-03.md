# After-action report: Shield boot outage, 2026-11-02 23:59Z to 2026-11-03 20:41Z

## Summary

A one-line systemd ordering mistake in a new Ethernet unit stopped the Shield from acknowledging a boot. That should have been a ten-minute fix. Recovery took about 20 hours of elapsed time and roughly 6 hours of hands-on owner time, because:

1. **The repair path itself corrupted the boot set.** From 17:25Z every write of the APP partition went through the NVIDIA bootloader's `fastboot flash system`, which damaged the kernel Image. The carrier then refused every boot on its hash check.
2. **The carrier failed silently.** It had no channel that reported why it refused, so about a dozen builds and reboots were spent testing guesses.

Omarchy has booted normally since 20:39Z. A reboot from Linux at 20:40Z came back in 62 s with every service active and the healthy acknowledgement written.

## Root causes

### Primary 1: systemd ordering cycle in `shield-ethernet.service`

`Before=NetworkManager.service` combined with `After=shield-owner-ready.service` closes the loop ready → sshd → network.target → NetworkManager → shield-ethernet → ready. systemd breaks the loop at a different job on each boot. When it dropped sshd, `shield-owner-ready` never ran, so the boot was not acknowledged and the next boot refused. The unit was never checked with `systemd-analyze verify` before it was enabled.

### Primary 2: `fastboot flash system` corrupts APP on this bootloader

Host fastboot converts a raw image into sparse chunks and turns any 4 KiB block made of one repeated 32-bit word into a FILL chunk. The kernel Image in the boot set has 215 such blocks. The Darcy bootloader's sparse writer (`device_write_sparse_image_recovery`, `write_fill_data`) writes those blocks wrongly. The ext4 metadata stays perfect, so `debugfs` and `e2fsck` on the host image show nothing. Only the content of `Image` is wrong.

The evidence holds up but stops short of a byte-level readback:
- **On-screen report:** carrier v12 printed `stage-failed: whole-artifact-hash` with nothing copied into the RAM directory, which means the first artifact (Image) failed.
- **Same content, different encoding:** the identical APP content written as RAW-only chunks booted immediately.
- **Every failure fits:** each boot after 17:25 was preceded by a fastboot APP write, and every successful boot on 11-02 followed a `dd` write.

### Contributing: no observability in the refusal path

- **The stage leaves no readable trace.** It writes its reason to a RAM directory and to kmsg, and neither survives into anything readable from recovery.
- **Recovery ADB over the PC cable stopped working at 03:27** and never came back today.
- **A USB stick could never work.** The recovery kernel builds usb-storage as a module that is not in the ramdisk, so the stick report never appeared.
- **"View recovery logs" is unusable.** It only lists the missing `/cache` logs.
- **After the watchdog is taken, a refusal parks the stage until a watchdog reset about 4 min later.** The menu stays on screen, so the refusal is invisible.

### Contributing: unguarded multi-step installs from recovery

The 03:27 install ran in recovery `sh`, which ignores `set -e`, on a 93 %-full partition. The `cp` failed and the script carried on, leaving an empty initramfs. Later scripts checked every step explicitly.

## What went badly in the response

- **Too many blind iterations.** Carriers v5 to v10 were each one owner round trip at the TV, each testing one guess with no readout. The beacon should have been the first tool built after the second unexplained refusal, not the eighth.
- **Wrong hypotheses, in order:**
  - a cable or VBUS problem (the owner rightly pushed back);
  - recovery's USB storage menu (the driver is absent);
  - the unit being a symlink (it was a regular file);
  - the misc flag booting the original recovery (ruled out by the RAM boot);
  - the boot reason (the first beacon run's code 6, still unexplained);
  - the framebuffer size.

  Each was plausible, and none was tested cheaply first.
- **`fastboot boot` (RAM boot) was assumed to work.** It stalls at the unlocked- bootloader warning screen when the controller is not responding, so the first RAM-boot "result" was misread.
- **The WSL disk filled to 100 %** during the work. Intermediates were cleaned up and two older APP backups compressed in place, and about 8.7 GB was free afterwards.
- **A destructive action with incomplete context:** the SanDisk stick that was wiped held the old USB root install. The owner approved the wipe, but I had not identified the stick first. A compressed image of that install remains in `usb-install-2026-10-15`.
- **Several watcher scripts killed themselves** with `pkill -f` patterns that matched their own command line, which cost time.

## What worked

- **The agent team** narrowed the field fast. The rescue architecture, fastboot capabilities and USB reports are reusable. The Fable deep researcher's FILL-chunk diagnosis was the turning point.
- **The beacon.** The light bar gave the first real signal (class, then detail, then boot reason), and the fixed framebuffer report gave the exact string.
- **Restoring the exact last-known-good configuration** set aside every change made during the day, so only the write method was left as a variable.
- **Preimage and readback checks** on every write, plus the timestamped ledger. Every partition state today can be reconstructed from `LEDGER-2026-11-03.txt`.

## Still unexplained

1. **Recovery ADB over the PC cable has not worked since 03:27.** The fastboot link on the same cable and port works. The USB agent's best explanation is VBUS sensing (GPIO Z0), which the bootloader fakes and recovery relies on. Forcing device mode through extcon (v10) did not help. The owner reports the cable worked all along.
2. **Beacon code 6 on the 20:09 run** (v2 stage, warm boot) was not reproduced. Possible strings include `system-tool-hash` and `APP-mounted-identity`. It may also be a side effect of the corrupt APP image, for example ext4 errors forcing a read-only remount.
3. **The USB Ethernet adapter never lit** in recovery or the bootloader. Its chip is unconfirmed. The recovery kernel has ASIX, AX88179, CDC and SMSC drivers, but not RTL8152.
4. **The first framebuffer beacon (v1) left the bootloader logo on screen.** The fix (unblank plus drawing every page) worked in v12, but the frozen logo before v12 was not fully explained.

## Rules from now on

1. **Never `fastboot flash system` a raw image.** Use `carrier/make-rawsparse.py` (RAW chunks only), or write APP with `dd` from Linux. `fastboot flash boot` and `recovery` with padded raw LNX/SOS images worked every time today.
2. **Nothing in the Shield's USB host port during a carrier boot.** The handoff refuses kexec when any device other than the root hubs is present (`internal-handoff.sh:188-193`), and a refusal after the claim leaves a pending record that blocks later boots.
3. **Verify every unit before enabling it:** run `systemd-analyze verify` on the unit and the default target, and never order an optional unit `Before=` anything in the acknowledgement chain (sshd, networkd, NetworkManager, `shield-owner-*`).
4. **Port roles:** the port farther from HDMI is the OTG/device port (PC cable, fastboot). The port beside HDMI is host-only (controller, adapters). Bootloader menu: hold A+B at power-on with the PC cable attached.
5. **Read the beacon first.** If the Shield lands in recovery, wait about three minutes. The screen then shows `SHIELD CARRIER BEACON` with the exact refusal; photograph it. The light bar codes are documented in `carrier/diag/shield-beacon.sh`.
6. **Multi-step device scripts** check every step explicitly and confirm free space first.

## Follow-ups, in priority order

1. **Rescue path** (`team-2026-11-03/rescue-architecture.md`, step 1): an unacknowledged pending boots a networked rescue initramfs instead of refusing. This needs an owner decision, because a failed boot would then end in a key-only root SSH shell on the LAN.
2. **Unit guardrail** (`rescue-architecture.md`, step 2): a `shield-unit-apply` helper that runs `systemd-analyze verify` and rejects ordering into the acknowledgement chain, plus a pre-change Btrfs snapshot.
3. **Fold the boot-reason relaxation into the carrier source of record**, rebuild the descriptor from it, and decide whether the beacon stays on the production carrier. It costs nothing on a good boot, because kexec ends it.
4. **Investigate recovery USB device mode** (unexplained item 1), or replace it with the rescue path.
5. **Carried over from 11-02:** read the real Bluetooth address from NCT; drop `modprobe.blacklist=r8169,pci_tegra`; fix the Ethernet IPv4 default route; fold the DT changes into `*.dtso`; remove patch 0018.
6. **Clean up the APP partition** (about 18 MB free before today): archive the unused `e8f146cd…` generation and the `*.bak` files off the device.
