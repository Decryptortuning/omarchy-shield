# Connected Darcy target

The latest locked-bootloader query returns `tegra210-darcy-p2894-0050-a04-00.dtb`, independently identifying the stock bootloader's A04 selection. The device returned to Android without unlocking or flashing. The [stock inventory candidate and receipt](STOCK_BOOTSTRAP.md) record that observation. Existing modern A08 components are evaluation builds; an A04 definition and reviewed memory handoff are required before a mainline hardware test.

The [latest integration build](INTEGRATION.md) supersedes the package versions in the historical build section below. It adds the Shield controller module and fan/PWM correction, verifies inactive firmware staging and passes the complete filesystem VM checks. [validation-darcy-integration.json](validation-darcy-integration.json) pins that candidate; physical acceptance remains zero.

The owner confirmed that the connected Shield is the device to convert. Read-only USB ADB inspection reports `darcy`, NVIDIA Shield Android TV, original Tegra210 A02, chip ID `0x21`, silicon major revision `1`, and revision enum `3`. Android is version 11, build `13961458_4387.0822`, on kernel `4.9.141-tegra`. This supersedes the initial assumption that the owner's box was a 2019 Pro. NVIDIA's [revision table](https://github.com/LineageOS/android_kernel_nvidia_linux-4.9_kernel_kernel-4.9/blob/929f123da07cc9f73af2861eccf5a01591794e52/drivers/soc/tegra/fuse/tegra-apbmisc.c#L170) distinguishes original Tegra210 from B01 using the hardware major revision.

The owner tentatively reads `P2897` on the enclosure. NVIDIA documents that model code in both its [2017 Shield declaration](https://images.nvidia.com/shieldwebsite/visuals/public/DoC/EN/SHIELD_TV_P2897_DoC_EN.pdf) and its [later Shield Pro declaration](https://www.nvidia.com/content/dam/en-zz/Solutions/SHIELD/support/shield-tv/shield-tv-pro-p2897-ce-doc.pdf). The enclosure model alone therefore does not establish the generation, internal board SKU or A08 PCB revision. This label is consistent with the connected device; the measured Darcy/original-Tegra210 identity remains the basis for the current kernel profile and 2017 recovery-family investigation. A part number has not been supplied.

The official NVIDIA Windows USB driver was downloaded from NVIDIA, its WHQL catalog signature verified, and installed with the owner's Windows administrator approval. Read-only fastboot inspection succeeded: `product=t210ref`, `secure=Yes`, `unlocked=No`, boot and recovery each `0x1980000` bytes (25.5 MiB), and a `0x02000000` maximum download size. `t210ref` does not identify a specific board SKU. Unknown SKU/revision variables were not treated as evidence. The Shield was returned to stock Android and ADB reconnected. No unlock, erase or partition flash occurred.

The stock partition links identify Android boot as `LNX`/`mmcblk0p18`, recovery as `SOS`/`mmcblk0p16` and the device-tree partition as `DTB`/`mmcblk0p17`. Fastboot uses the names `boot` and `recovery`; it rejects the raw NVIDIA partition names queried here. These are observations, not flashing instructions. Direct ADB reads of boot/recovery, device-tree values and vendor firmware are blocked. Only the stock kernel configuration and accessible metadata have been captured; there is no raw stock boot backup yet.

The default [kernel.lock.json](kernel.lock.json) selects the pinned ACK kernel and `tegra210-p2894-0050-a08.dtb`, with [hardware-darcy.json](hardware-darcy.json) as its 19-subsystem acceptance matrix. This is an evaluation DT for the correct SoC generation, not proof that A08 is the owner's exact SKU. Its SDIO radio and PCIe Ethernet topology need comparison with the stock board. The separate [kernel-mdarcy.lock.json](kernel-mdarcy.lock.json) retains the B01 B00 candidate. Platform detection, Linux evidence collection, USB diagnostics and package staging reject crossed board/SoC combinations.

The original Tegra210 XUSB firmware and generic BCM4354 SDIO firmware are present in the development filesystem. The [integration harvest](HARVEST.md) now holds exact-release radio calibration, Bluetooth and media firmware locally, with provenance and inactive upstream candidates. They have not been integrated into the runtime or physically qualified. Native graphics, cooling and all physical acceptance remain open. A 2019-only AI upscaling feature is not an acceptance requirement for this original-X1 hardware; capabilities actually present on the owner’s Shield remain in scope.

The [board-source investigation](BOARD_SOURCES.md) now pins the original Darcy vendor DTS, LineageOS compressed-kernel/boot-image recipe and exact Wi-Fi/Bluetooth firmware mappings. Board and driver reference data is available; the remaining work is matching and integrating those inputs on this device. This research does not change the previously built artifacts or their validation receipt.

## Native boot prerequisites

The raw `Image` is 45,746,688 bytes, exceeding both the observed 25.5 MiB boot partition and 32 MiB download limit. `Image.gz` is 17,246,875 bytes; together with the 732,023-byte diagnostic ramdisk and 72,330-byte evaluation DTB, its raw payload fits that partition before header/alignment overhead. This is a size check only. Exact installed-build stock images now establish gzip kernel payloads, Android header version 1 and 2,048-byte pages. The raw address fields need CBoot-specific interpretation and are not verified physical load addresses.

LineageOS source independently specifies `Image.gz` and Android header version 1. It also documents that the Mdarcy/Sif recovery-DTBO handoff is ignored on older platforms. Its bootloader allowlist and recovery-partition size differ from the owner's observations. The stock kernel enables legacy kexec, providing a candidate explicit-DTB handoff after controlled privileged stock-kernel entry; neither entry nor handoff is tested. No P2894 U-Boot configuration is qualified.

The [boot harvest](harvest/boot.json) obtained official Shield Experience 9.2.4 boot and vendor inputs matching installed build `13961458_4387.0822`. The embedded kernel configuration is byte-identical to the earlier stock capture. Local BSDIFF40 reconstruction produces a 20,575,528-byte recovery matching NVIDIA's target digest; boot/recovery RSA/SHA-256 footer checks pass using their embedded certificate. The whole OTA signature and hardware trust-anchor match remain unverified. This closes the release-input gap, but does not provide a physical partition backup or tested restoration route. The older developer-catalog 9.2.1 archive remains login-gated and is not selected for downgrade.

Before any device write, the remaining work is to confirm the actual board SKU and memory handoff, review boot addresses and device-tree entry, qualify restoration and prepare a recoverable diagnostic boot. The locked bootloader prevents a native test at this stage; unlocking would erase Android user data and requires a separate owner decision after the boot/recovery preparation is reviewable. The ARM development filesystem still contains build accounts and signing state and is not an installable SSD image.
