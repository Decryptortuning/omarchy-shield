# Stock-kernel inventory entry candidate

## Native entry results

On October 15, owner-approved unlocking completed in 394.918 seconds and subsequent fastboot queries verified `unlocked: Yes` on the same A04-selected Darcy. Temporary boot commands for both this candidate and the untouched matching NVIDIA recovery returned `OKAY`, but both attempts reached Android welcome/setup. Installed stock recovery then worked through **Boot recovery kernel**. Its ADB update mode provided sideload transport, but no shell; no update package was sent.

The owner subsequently authorized diagnostic installation with matching fastboot restoration available. A reviewed `fastboot flash recovery stock-inventory.img` completed successfully in 0.904 seconds. Selecting **Boot recovery kernel** again returned to Android welcome/setup. The 90-second collector received no diagnostic USB interface and saved no archive. No other partition image was flashed. [validation-native-entry.json](validation-native-entry.json) records the inputs and outcomes. Command acceptance does not qualify kernel or ramdisk execution; the cause remains unresolved.

The exact-release `install-recovery.sh` checks the recovery partition against the stock size/digest and reconstructs it from the boot image and vendor patch when they differ. This establishes that normal Android can overwrite custom recovery; it does not prove that replacement happened or explain the first failed custom boot. Current recovery contents are unverified, and matching stock recovery has not yet been restored by this work. The next control is a matching stock recovery write followed immediately by the same menu entry, without an intervening Android boot. The [maintainer installation guide](https://wiki.oddsolutions.us/devices/foster/install/variant1/) independently documents that sequence and the overwrite behavior. **Forced Recovery** is the separate low-level Tegra USB recovery mode.

NVIDIA's [published kernel source](https://gitlab.com/nvidia/nv-tegra/linux-4.9/-/blob/e7d2f8cc12ddadad5664014cc79eeb528a65646a/init/initramfs.c#L610) shows that bare `skip_initramfs` discards a supplied ramdisk; `rdinit=/init` cannot recover it and adding `skip_initramfs=0` cannot negate the flag. That source is from the neighboring 9.2.2 release. The exact 9.2.4 kernel configuration has `CONFIG_DIAG_KERNEL` unset, consistent with this mechanism. A [Darcy owner's report](https://github.com/topjohnwu/Magisk/issues/8297#issuecomment-5081662390) describes this argument under LineageOS with the same bootloader version. These are leads for the RAM boot results, not proof of our recovery-mode arguments. Early inventory guards can also stop before USB setup, and stock's disabled VT console makes their messages invisible on HDMI. Execution logs are needed before choosing a fix.

An offline comparison downloaded the official [October 5 foster recovery](https://mirrorbits.lineageos.org/full/foster/20261005/recovery.img) and verified its [published hash](https://download.lineageos.org/api/v2/devices/foster/builds): 21,917,696 bytes, SHA-256 `99a0b27ed43d16fc1a9a7995f4b4428f1761c0216932dd9599400bbaa6b6cf9b`. Its declared aligned payloads occupy the whole file, with no appended legacy BootSignature footer. Its [pinned source](https://github.com/LineageOS/android_device_nvidia_foster/blob/666d034739cd89e5a2628129e2141927e9d65592/AndroidBoard.mk) includes Darcy A04; its kernel differs from NVIDIA stock. This weakens a mandatory-footer hypothesis without proving compatibility with the current physical bootloader. It has not been flashed. The matching recovery implementation provides [Advanced → Enable ADB](https://github.com/LineageOS/android_bootable_recovery/blob/b7461833c7a75c00417208d61ee4c173c645dc1a/recovery.cpp#L626) for main-menu shell access, making it a possible later recovery-only control. Its full ROM updater can write other boot-chain components and is outside this diagnostic comparison.

## Built candidate

The locally built image is **12,384,256 bytes**, SHA-256 `2f37d27e9b7c1a17cd777adf35c622314bce5dc98927f8a7593b4788f9d29a1e`. Its independent pinned-AOSP repack is byte-identical. The ramdisk starts under the modern kernel on QEMU `virt`; 30 Python tests, ShellCheck and the Windows CI binary-stream parser tests pass. [validation-stock-bootstrap.json](validation-stock-bootstrap.json) records the exact scope. Neither the stock kernel on real hardware nor physical USB/cooling has been qualified by those virtual tests.

An October 14 documented read-only `fastboot oem dtbname` query returned `tegra210-darcy-p2894-0050-a04-00.dtb` while the owner device remained locked. It was returned to Android with authorized ADB connected. This independently establishes the bootloader's **A04 selection**; no PCB EEPROM or part number was read. The existing modern A08 evaluation profile needs an A04 definition before a mainline hardware test. This stock-kernel inventory candidate preserves the current bootloader/DTB handoff.

This is a separate first-stage diagnostic candidate. It uses the exact installed-release stock recovery kernel and preserves its header load-address fields and existing bootloader/DTB handoff. It replaces the ramdisk and command line, updates the Android image digest and omits the original signature footer. It requires an unlocked bootloader. Preserving measured fields does not qualify their effective addresses or prove that temporary boot works.

The independently inspected `stock-bootstrap.lock.json` pins the stock recovery, matching fan/thermal modules, XUSB firmware, BusyBox archive and kexec source. `prepare-stock-bootstrap.py` keeps every header byte outside the ramdisk size, command line and digest ranges unchanged. The kernel payload remains byte-identical. No DTB, partition table or early boot firmware is included for replacement.

The inventory init requires explicit opt-in, original Darcy compatible strings, chip ID 33/major revision 1 and stock kernel release `4.9.141-tegra`. It uses the same two cooling modules and load order as the matching recovery. It runs no Android installer/service and mounts no persistent filesystem. A short idle session records DT identity, available live FDT, memory maps and logs under `/run/shield-stock`. GPT labels independently select bounded read-only boot/recovery/DTB backups into RAM. Missing labels or unavailable FDT remain visible gaps; nothing is inferred from the evaluation A08 DTB.

USB serial uses stock's `700d0000.xudc` controller and built-in ACM function. The root console is intended only for this physical diagnostic session. The session powers off after 60 seconds, sooner for a detected 70°C CPU/GPU reading or absent plausible sensor data. It runs no kexec operation automatically. Evidence disappears at power-off unless transferred to the PC; any real device dumps must stay private until reviewed.

The Windows [collector](tools/collect-stock-inventory.ps1) waits for a unique USB serial interface whose parent has the inventory gadget's VID/PID and explicit serial string. It opens no arbitrary COM port. Its fixed command creates a tar in device RAM and transfers a nonce/length-framed binary stream into a new private PC directory. It bounds the transfer and saves a SHA-256 receipt; it never extracts or publishes the archive, writes a device partition or invokes kexec. Start it before a separately authorized temporary boot so collection fits the bounded session. Synthetic binary-stream tests do not qualify physical USB enumeration or transfer.
